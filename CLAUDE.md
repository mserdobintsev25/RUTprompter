# RUTprompter — контекст проекта для Claude Code

## Что это

RUTprompter — настольное приложение-суфлёр (teleprompter) для macOS.
Ориентир по базовым возможностям — easyprompter.com, но с одним
принципиальным отличием: RUTprompter не просто крутит текст с заданной
скоростью, а **слушает речь выступающего и подгоняет скорость прокрутки
под неё в реальном времени**, плюс показывает динамическую оценку
оставшегося времени чтения.

Это готовится как самостоятельный проект под отдельную рабочую сессию
Claude Code (вкладка Code с папкой `RUTprompter`). В этом файле — весь
контекст, который должен быть у агента перед началом кодирования.

## Сценарий использования

Это НЕ эфирное/студийное приложение — автор снимает с партнёром
короткие вертикальные видео (кулинарные форматы с диалогом, разные
шутки/приколюхи). Важные следствия для дизайна:

- Live-эфиров и жёстких хронометражей передачи нет, но есть целевая
  длительность конкретного видео/дубля (под формат площадки — шортс,
  рилс и т.п.) — поэтому "целевая длительность на текст" важна, а
  "рундаун нескольких скриптов подряд, как на ТВ" — не нужен.
- На площадке обычно два человека и разговор идёт постоянно — читает
  скрипт не всегда один и тот же голос, и второй человек может
  говорить поверх/рядом. Значит важно отличать голос читающего от
  голоса собеседника (см. диаризация ниже), а не просто ловить любую
  речь в комнате.
- Дубли переснимаются, формат неформальный — отсюда нужны пост-анализ
  дублей и устойчивый ручной override, а не сложные механизмы live-
  восстановления после эфирного сбоя.

## Ключевая фишка (главный дифференциатор)

- Приложение непрерывно распознаёт речь спикера (on-device speech
  recognition, без отправки звука куда-либо).
- Распознанные слова сопоставляются с текстом скрипта (с учётом
  возможных ошибок распознавания, пропусков, повторов, "воды").
- По результатам сопоставления вычисляется реальный темп речи (слов
  в минуту, WPM) с плавным сглаживанием (EMA / critically-damped
  spring), чтобы не было рывков.
- Скорость автопрокрутки строки подгоняется под этот темп — прокрутка
  "следует" за голосом, а не идёт по заранее заданному расписанию.
- Поверх этого в реальном времени считается и показывается
  **ориентировочное время до конца текста** (исходя из оставшегося
  количества слов и текущего измеренного темпа речи) — обновляется
  непрерывно, а не один раз при старте.

## Что должно быть, как в референсе (easyprompter.com)

Исследование страницы easyprompter.com показало следующий набор
возможностей, который стоит учитывать как базовый уровень:

- Мультиэкранный вывод: один прибор/окно управляет текстом, все
  подключённые экраны синхронно показывают одну и ту же позицию в
  скрипте.
- У каждого экрана вывода — свои настройки: размер текста, отступы,
  зеркалирование, маркеры, таймер, полноэкранный режим, скрытые
  элементы управления.
- Зеркалирование текста для стеклянных суфлёрных насадок — при этом
  окно оператора остаётся в нормальной (не отражённой) ориентации.
- Профили спикеров (сохранённые настройки чтения/отображения под
  разных выступающих).
- Библиотека/коллекции скриптов, офлайн-доступ к сохранённым скриптам.
- Удалённое управление воспроизведением (с телефона или физических
  контроллеров) — для RUTprompter на первом этапе не приоритет, но
  архитектуру стоит делать так, чтобы потом не пришлось всё
  переписывать.

На странице явно НЕ упоминаются (то есть это наше преимущество):
распознавание речи / автоподгон скорости под спикера, оценка времени
чтения в реальном времени, явная поддержка HDMI, цветовые темы.

## Главное требование по экранам (из задачи)

- **Основной экран (ноутбук)** — окно оператора: он видит текст в
  нормальной ориентации, может на лету править текст, двигать скорость
  руками, менять настройки.
- **Второй экран (через HDMI)** — зеркальное отображение (или просто
  "чистый" полноэкранный вывод без элементов управления) — для этого
  экрана должна быть отдельная настройка зеркалирования (включается
  независимо от окна оператора).
- Окно оператора и окно вывода — это два разных NSWindow с разным
  содержимым/трансформацией, синхронизированные по позиции скролла, а
  не "один и тот же экран, растянутый на два монитора".

## Требования к читаемости/интерфейсу

- Высокая контрастность текста (несколько готовых пресетов: белый на
  чёрном, жёлтый на чёрном, чёрный на белом + свой кастомный выбор
  цветов текста/фона/подсветки текущей строки).
- Крупный, адаптивный размер шрифта, настраиваемые отступы/межстрочный
  интервал.
- Приятный, аккуратный интерфейс самого оператора (не только вывода).
- "Выключка" (цветовая схема/тема оформления текста) — должна быть
  полностью настраиваемой, а не ограничена готовыми пресетами из
  референса.

## Рекомендуемый стек

Нативное приложение под macOS: **Swift + SwiftUI/AppKit**, Swift
Package Manager — так сделаны остальные личные Mac-утилиты автора
(см. проект Peel: `Package.swift`, `Sources/<Name>/`, `CLAUDE.md`,
`README.md`, `TASKS.md` в корне). RUTprompter следует той же
структуре для единообразия.

Причины выбора нативного стека, а не Electron/web:
- Нужен точный контроль над размещением окна на конкретном физическом
  дисплее (включая HDMI) и полноэкранным режимом именно на нём —
  `NSScreen.screens` даёт это напрямую.
- On-device speech recognition лучше всего доступен через системный
  `Speech` framework (`SFSpeechRecognizer`, `requiresOnDeviceRecognition
  = true`) — работает офлайн, не гоняет звук на сервер.
- Нет нужды в Node/Electron overhead для простого full-screen окна с
  текстом.

## Архитектура (черновая, уточняется в процессе разработки)

- `PrompterDocument` — модель скрипта: текст, разбитый на слова/абзацы,
  маркеры (закладки для быстрого перехода).
- `SpeechPacer` — слушает `SFSpeechRecognizer`, сопоставляет
  распознанные слова с ожидаемыми словами скрипта в окне поиска
  (lookahead), двигает указатель текущей позиции, считает
  сглаженный WPM по таймстемпам распознанных слов.
- `ScrollController` — превращает позицию указателя в целевой scroll
  offset и анимирует к нему (плавно, без рывков), даже если
  распознавание на секунду "потерялось".
- `TimeEstimator` — оставшиеся слова / текущий сглаженный WPM = ETA,
  обновляется каждый тик.
- `PrompterTheme` — настройки цвета текста/фона/подсветки строки,
  шрифта, отступов; хранится в `UserDefaults`/JSON, есть пресеты и
  кастомный режим.
- `DisplayManager` — следит за `NSScreen.screens`, определяет внешний
  (HDMI) дисплей, открывает/закрывает на нём отдельное
  `NSWindow` в полноэкранном borderless-режиме; применяет
  зеркалирование (`CGAffineTransform(scaleX: -1, y: 1)`) только к
  этому окну, независимо от окна оператора.
- Окно оператора (`OperatorWindow`) — редактирование текста,
  индикатор текущего WPM, оставшееся время, элементы управления
  (play/pause, ручная подстройка скорости, маркеры, темы, вкл/выкл
  зеркала на втором экране).

## Соглашения проекта (по аналогии с остальными утилитами)

- Правки вносятся в сессии Claude Code, открытой именно на папке
  `RUTprompter`.
- Перед изменением — смотрим текущий код и `git status`.
- Одно изменение за раз, с понятным критерием готовности (собралось /

- Локальный коммит — по отдельной просьбе, не автоматически.
- Следующие идеи и нерешённые вопросы — короткий список в `TASKS.md`.

## Жёсткое ограничение

**Голосовое управление командами ("стоп", "дальше", "назад" и т.п.)
запрещено как фича, не просто неприоритетно.** Причина: на площадке
постоянно идёт обычный разговор (кулинарный/разговорный формат), и
случайно сказанное в диалоге слово не должно останавливать или
перематывать прокрутку. Голос используется ТОЛЬКО для пассивного
трекинга темпа чтения скрипта, никогда — как интерфейс команд.

## Диаризация (кто сейчас читает скрипт)

Нужно отличать голос читающего скрипт от голоса собеседника, чтобы
болтовня второго человека не сбивала трекинг. Технически это не
решается одним SFSpeechRecognizer "из коробки" — он не делает speaker
diarization. Реалистичные варианты, которые стоит оценить на этапе
разработки (не предрешено, какой выбрать):

- Привязка к конкретному входному микрофону/каналу (если у каждого
  свой мик/лавалье — технически самое надёжное и простое решение).
- Контентное сопоставление само по себе уже отчасти справляется:
  реплики собеседника, которых нет в тексте скрипта, просто не
  продвигают указатель позиции — алгоритм `SpeechPacer` и так
  игнорирует нераспознанные-как-скрипт слова.
- Полноценная speaker-embedding диаризация (сравнение голосового
  отпечатка с заранее записанным образцом голоса читающего) — самый
  надёжный, но самый трудоёмкий вариант; рассматривать как улучшение
  поверх контентного сопоставления, а не как блокер MVP.

## Открытые вопросы (требуют решения на этапе разработки)

- Какой язык распознавания делать основным — скорее всего нужна
  смешанная ru+en модель/переключение внутри одной фразы, а не только
  ru-RU (в кулинарных и шуточных текстах часто есть иностранные слова
  и термины).
- Нужен ли отдельный "безопасный" fallback-режим прокрутки по
  фиксированной скорости, если распознавание речи недоступно
  (нет доступа к микрофону, нет сети для первой загрузки модели и т.п.).
- Нужна ли поддержка внешних контроллеров (клавиатура точно нужна,
  Stream Deck/педали — опционально, как в референсе).
- Какой вариант диаризации брать за основу на старте (см. раздел выше).

## Технические заметки (после первой реализации)

- Сборка только через Command Line Tools (Xcode нет): в них нет плагина
  макросов SwiftUI, поэтому `@State` не компилируется — используйте
  `@StateObject private var x = StateBox(...)` (см. `Settings.swift`).
  XCTest тоже недоступен — логика проверяется `./build.sh check`.
- Логика без UI — в таргете `PrompterCore`; новые алгоритмы сначала
  покрывать проверками в `Sources/CoreChecks/main.swift`.
- Позиция везде измеряется в словах (`Double`), пиксели считает только
  `PrompterCanvasView`.
- Голос проверяется БЕЗ звука: начитка в файл `say -v Milena -o take.aiff "…"`
  (`[[slnc 4000]]` — пауза), затем
  `defaults write local.rutprompter.app rut.testAudioFile /путь/take.aiff`
  и `rut.speechDebug -bool true` — журнал в
  `~/Library/Application Support/RUTprompter/debug.log`. После теста оба
  ключа убрать. Звук на динамики не выводить: автор работает в коворкинге.
- Две on-device модели распознавания в одном процессе обрывают друг друга —
  используется только одна.
